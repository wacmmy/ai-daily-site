Guillermo：发布 xeet，不启浏览器也能把 X 帖渲成像素级一致的 PNG
1. Guillermo Rauch（@rauchg）发帖介绍 xeet。它用安全 Rust / WASM（项目写明 `#![forbid(unsafe_code)]`），在无浏览器、无网络、无文件系统、也不依赖系统字体的条件下，把一条 X 帖渲成与 Chrome 在 x.com 上所见一致的 Retina PNG。发帖里写，渲成 PNG 约 1ms（Jack 那条 “setting up my twttr” 约 0.4ms），比拉起浏览器再截图快 100–1000 倍。项目站点补充的实验室数字是：文本帖 p50 为 2.8ms（390px、3×），带四个媒体占位为 4.5ms。它复现 Blink 与 HarfBuzz 文本排版、1/64px 换行、RTL / CJK / 数学 / Emoji 回退、「Show more」规则，以及 28 套 Chirp 字体子集。项目按「autorepo」和 verification engineering 来组织：一个 oracle 启动 Chrome，核对成千上万条文本排版规则；CI canary 盯着上游界面变化，给 agent 提签名 PR。演示和 playground 在 xeet-rs.vercel.app，仓库是 github.com/rauchg/xeet，并提供 `@xeet/core` 和 CLI。
背景：昨天简报里他用 fx 和 UI SDK 做过 Winamp 风格播放器，那是一次演示；xeet 是独立的新渲染器，面向发帖前预览，以及 agent 预览。
实际影响：要在发帖前核对版式，或让 agent 生成准确的帖子图，可以直接用站点 playground，或按文档把核心接到自己的流水线，而不必每次启动无头浏览器。

Tibo：Codex「model at capacity」错误占比已降到很低，称可能已经修好
2. Thibault Sottiaux（@thsottiaux，Codex 与 ChatGPT，OpenAI）发帖：「Codex team might have actually fixed the "model at capacity" errors that have been pestering you.」配图是一张图表，标题为 “Codex users hitting a capacity error”，时间窗是 2026-10-15 至 2026-11-12（UTC），指标是「Share of daily active users with at least one turn ending in a capacity error」（当日活跃用户里，至少有一轮以容量错误结束的比例）。曲线在 10 月 19 日附近见顶 6.82%，之后反复波动。图上标了 6 次 Retry-After 相关发布：10 月 15 日桌面版带上 WebSocket retry 修复；10 月 22 日 Responses 在普通过载时加延迟；10 月 23 日服务档过载也有重试时间；10 月 24 日 Codex 会转发 retry 和 stop 指令；10 月 30 日 Responses 为 NO_MORE_RETRY 加延迟；11 月 6 日 Responses 在 WebSocket 错误里也保留该延迟。图上最后标出的点是 11 月 12 日的 0.085%。他用了 “might have actually fixed”，图只画到 11 月 12 日，没有宣布已经彻底清零。
背景：容量错误会让 Codex 对话中途失败，是近期用户常见抱怨；这是他用内部指标做的进度说明，不是新功能发布。
实际影响：最近仍常碰到 “model at capacity” 的人可以再试；若仍然频繁出现，说明你这边的情况可能还没被这张截至 11 月 12 日的图覆盖，不宜当成已经完全修好。

Peter Steinberger：macOS 27.3 给 AI 应用加更醒目的权限警告，本地 agent 更难「放下不管」
3. Peter Steinberger（@steipete）引用 MacRumors 报道并写道：人们希望减少权限弹窗，好让 agent 在 macOS 上少人看管；苹果的回应是「给你一些新的吓人提示」。MacRumors（2026-11-16）写：在最新 macOS 27.3 beta 里，苹果向开发者通报将改 Full Disk Access API，以及 Device Control and Data Access API。原来的 Device Control and Data Access 将拆成 System & App Protection Override 和 Accessibility；鼓励只给工作流所需的应用或文件夹授权；用户可以把应用设成每次询问，而不是一次给满权限；当一个应用通过 System & App Protection Override 控制另一个应用时，菜单栏会有透明度指示。开发者需要调整引导，并在只能访问有限文件夹或应用时优雅降级。已知应用在 27.3 之前已授予的权限仍然有效；用户会在批准新的权限请求时看到这些变化。苹果上月已表示，因 AI agent 的风险，会给 Full Disk Access 加更多控制。
背景：越来越多人在本机跑 coding agent，常申请辅助功能或完全磁盘访问；这是系统层面对这类权限的收紧，不是某一家 agent 产品自己的更新。
实际影响：在 27.3 beta（以及后续正式版）上跑本地 agent 的人，可能会看到更明确、也更劝退的授权流程，以及菜单栏指示；需要完整磁盘权限的工作流，可能要改成就地申请，或只打开必要目录。
社区讨论：Peter 在回复里说「move to cloud agents. local isn't the future」（这是他的观点），并称自己用 openclaw、crabbox 和 podman 在自有基础设施上跑；他后来又说，苹果并没有修好问题，只是让现在能做的事更难了，还提到完全空的开发用 Mac，也会因为「保护空文件夹」而拦住 agent（这是他的使用经验）。评论区也有人认为，把风险说清楚是应该的。系统改动以报道为准；「云端才是未来」和「没有修好」是他的判断。

Vercel AI Gateway 上线 Private Inference；Guillermo 给出「Own your intelligence roadmap」
5. Vercel 官方账号宣布：Private Inference 已在 AI Gateway 上线。调用形式为 `private/<slug>`，可以把自有的微调、自托管或尚未发布的模型，和目录里的模型一起用，并共用同一套 API、认证和日志。Guillermo 引用该帖，列出四条「Own your intelligence roadmap」：① 使用开放的 SDK 和 harness；② 用 Gateway 自己选择模型；③ 自己掌握 traces 和数据，并执行 ZDR（Zero Data Retention）；④ 用 private inference 掌握自己的模型。
背景：AI Gateway 过去主要是接入目录模型；这次是把私有或自托管模型收进同一网关。ZDR 是他提纲里提出的要求，不是这条公告新定义的条款。
实际影响：已经在用 AI Gateway 的团队，可以用 `private/<slug>` 把内网或自训模型接到现有调用方式里，而不必为私有模型另铺一套鉴权和日志。具体开通步骤以 Vercel 后续说明为准。

Vercel 博文：agent 也是用户，软件需要 eval；Guillermo：用 eval 驱动工程循环
6. Vercel 于 2026-11-16 发表博文《Agents are users, so your software needs evals》（作者 George Fahmy、Yury Selivanov）。文中把 agent 使用产品的路径写成 Discovery、Selection、Access、Success，并重点讲 Success：不能只看请求是否成功，而要多次跑同一任务并打分。测试按 LLM 调用次数分成金字塔：确定性测试（0 次）、一轮 eval（1 次）、端到端 eval（2 次及以上）。文中用开源框架 Harbor（来自 Terminal-Bench 作者）举例，在 Vercel Sandbox 和 AI Gateway 上搭端到端 eval，并讨论 pass@k 与 pass^k 的取舍。Guillermo 转发说：旧方式里用户是人，做访谈和用户旅程；新方式里用户是 agent，跑 eval，eval 再进入软件工程循环，并称这是一篇讲 Vercel 如何做 eval 的好文章。
背景：这是一篇工程方法文，不是新的计费产品；Harbor、Sandbox 和 AI Gateway 都是已有工具，文章是把它们串成可执行的 eval 做法。
实际影响：在做 API、CLI 或 MCP、希望 agent 能稳定完成任务的人，可以按文里的金字塔从确定性测试补起，再用 Harbor 做少量端到端任务，而不是只靠一次手工试跑。
