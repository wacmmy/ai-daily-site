Anthropic：Messages API 从 Python 迁到 Rust；Amjad：能验证，大规模迁移就可行
4. Anthropic 官方账号在 11 月 26 日 0:26（上海时间）发帖，并发布工程博客《Migrating our Messages API to Rust》（标注日期 11 月 25 日）：Messages API 已从 Python 迁到 Rust。这篇 API 是客户以及 Claude Code、Cowork 等自家应用调用 Claude 的主要入口。博客写，从 2024 年初到 2026 年秋，API 流量大约增长了 1800 倍。Claude 大约用一周写出了核心请求路径的第一版，但更难的是证明新版与线上 Python 版行为一致：生产服务仍在改、同一请求的回复本身就有随机性，而且他们不能阅读客户请求。他们把线上的 Messages API 本身当成 verifier，在生产流量上对照差异，并自动派 agent 去修。最终在不停机、也不冻结功能开发的情况下完成切换：每请求 CPU 大约减少 70%，到第一个 token 的中位时延大约降低 20%。他们也曾先把解析模型输出的部分改成 Rust、再由 Python 调用，CPU 只降了约 8%–10%，还让每个 token 在两种语言之间来回三次，得不偿失。博客还写，到 2026 年 5 月，Anthropic 合入的代码里已有超过 80% 由 Claude 编写；原有约 700 个集成测试不够用，移植后审计发现 100 多项断言被削弱。Amjad Masad（@amasad）在 2:56 引用这篇博客写：只要能验证结果，大规模软件迁移已经可行；考虑到仍在跑关键基础设施的老旧系统，这一点特别重要。
背景：这是 Anthropic 自己的一次生产迁移复盘，不是对外发布新的迁移产品。近 7 天 Builders 简报没有报过此事。
实际影响：用 Messages API 的人会看到官方给出的效率数字，但博客没有要求调用方改接口。想做同类迁移的团队，重点是先建立可自动对照的验证方式，而不是先追求一次写完。

Guillermo：Workflow SDK 再提速，fx 发布 0.0.18
5. Guillermo Rauch（@rauchg）在 11 月 26 日 4:18（上海时间）转发 Vercel 官方说明：Workflow SDK 再次快了约 10 倍。官方 changelog 标注为 11 月 25 日，版本是 Workflow SDK 5.8，换了新的执行引擎。官方数字是：步骤与步骤之间的时延降到原来的 1/12（评测里 p75 开销从 85 毫秒降到 7 毫秒）；大规模并行（例如 256 个步骤一起跑）在步骤代码之外的函数时间降到约 1/14；幂等步骤会做推测执行。Vercel 官方帖还写，durable agent 的回合快了 3.8 倍。changelog 举例：一个五轮、带流式 token 和工具调用的 agent 循环，额外开销从 3.0 秒降到 0.9 秒。Guillermo 说，对需要 harness 持久化的系统（他点名 @eve、libfx、pi、opencode），这能压低回合之间的等待。升级到 `workflow@latest`（changelog 写明是 `workflow@5.8.0` 或更高），不必改代码；已经在旧引擎上跑着的任务会继续用旧引擎，新任务默认走新引擎。官方提醒：步骤尽量做成幂等，才能吃到这次升级。
同一天稍早，Vercel 发布 fx v0.0.18，Guillermo 转发并写：随着模型变强，权限、diff、命令、工具调用这些实现细节会淡掉，harness 本身也会淡掉，它变成高性能的代码和命令执行层，加上一层持久存储。他还写，fx 仍然只有约 6MB，却已经包括 subagents、MCP、skills、sessions、durability、ACP、TUI 和网络传输。changelog 标注日期为 11 月 25 日，二进制约 6.87MiB：subagent 停止和恢复更稳，工具视图更紧凑，配置了 MCP 时 shell 命令快 3.1–4.8 倍，同一 profile 下的多个 session 可以共享一份 stdio MCP 服务器，另外还有多项修复和安全改进。
背景：昨天 Builders 简报写过 Guillermo 解释 fx 是 libfx 的薄封装。本期新的是 Workflow 引擎提速和 fx 的 0.0.18 版本，不是 fx 首次发布。
实际影响：已经在用 Vercel Workflow 的人可以升到 5.8，正在跑的旧任务不会被强制切换；用 fx 的人可以按 changelog 升到 0.0.18。做 durable agent 的人，如果步骤不是幂等的，推测执行带来的收益会受限。

Google Workspace：MCP 服务器和官方 CLI 正式可用，2027 年 2 月起 agent 须走 MCP
6. Peter Steinberger（@steipete）在 11 月 26 日 2:15（上海时间）发帖，对 Google 推出 MCP 之后的政策表示不满，并问这是否等于禁止 gog 这类 CLI，除非付更多钱。他引用的是 Google Workspace 官方博客（标注日期 11 月 24 日；近 7 天 Builders 简报未报）。博客宣布：Workspace MCP 服务器和官方 Workspace CLI 正式开放。MCP 服务器面向云和网页端 agent，覆盖 Gmail、Drive、Docs、Sheets、Slides、Calendar、Chat 和 Tasks（Keep 即将加入）；官方 CLI 面向本地终端、虚拟机和容器沙箱，带打包的 agent skills、动态命令发现和范围登录。与此同时，Workspace API（先从 Gmail、Drive、Calendar 开始，MCP 和 CLI 也适用）分成两档：Standard 免费并有公开配额；Scaled 面向需要更高配额的项目，从 2027 年 4 月 1 日起，超出每日免费额度的部分才收费。如果到期未操作，项目可能会被限到已公布的 Standard 配额。对 AI agent 或类似访问工具，必须通过 MCP 访问 Workspace 数据，不能再直接调用 Workspace REST API，技术强制从 2027 年 2 月 1 日开始。博客写，目前超过 99% 的活跃开发者仍在 Standard 档内，可继续免费使用。组织内部使用的项目可由管理员标为 internal，较高限额仍包含在 Workspace 订阅里。博客还宣布了 Workspace AI Tools Addendum，以及管理控制台里的 agent 访问管理、人在回路确认和审计日志。
背景：这是 Google 为 agent 访问 Workspace 定下的官方通道和配额规则。Steinberger 维护的 gog 等第三方 CLI 是否被直接禁止，官方文中没有点名，这里不把个别工具的命运写成既成事实。
实际影响：在做 Workspace agent 的人，需要在 2027 年 2 月 1 日前把 agent 访问改到官方提供的 Workspace MCP 服务器或 Workspace CLI，并在 Google Cloud 控制台把用于 agent 的 OAuth 客户端标为 AI-powered agent（is_agentic）。若用量会超过 Standard 配额，要在 2027 年 4 月 1 日前改到 Scaled，或把仅限组织内部的项目标成 internal。可先看 Workspace API usage developer dashboard。
社区讨论：Steinberger 的判断是 Google「终于做了 MCP，却在限制 gog 这类 CLI，除非多付钱」。前半句对应官方已推出托管 MCP 和官方 CLI，后半句是他对第三方 CLI 和 Scaled 收费的看法，不是官方原文。

Aaron Levie：同一公司里，AI 采用差距可以到 10 倍
8. Aaron Levie（@levie）在 11 月 25 日 12:11（上海时间）发帖：一年前听起来还不现实的事，现在更说得通了——靠最近的模型和 harness 进展，产出可以有 10 倍提升。结果是，同一家公司里的不同团队，会因为 AI 用得深浅，拉出非常不同的产出。他认为这和其他技术不一样：过去谈数字化或上云，多半是公司一级的统一采用，各团队提升幅度差不多；AI 则可能在同一家公司内部，最低和最高采用者之间出现 10 倍差距。那些真正能改流程、把 agent 嵌进工作流的团队，按岗位不同，生产率可以有一个数量级的跳变。他写，眼下这主要集中在写代码，但会有更多工作变得接近编码，其他职能也可能出现类似结果，公司内部会因此出现很不一样的动态。他引用的是 Ethan Mollick（@emollick）的观察：在制造、金融服务等大型机构里，已经出现三两个人的小团队用 AI 做完过去几十人的工作，并在管理层引发关于影响和内部政治的争论。
背景：这不是新的产品发布，而是对已经能看到的采用差距的判断。近 7 天 Builders 简报没有报过这一观察。
实际影响：在公司里推 AI 时，不能只看「公司有没有采购」，还要看各团队有没有改流程；编码团队的差距可能最先拉大。
